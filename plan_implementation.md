# План реализации Add-in EPLAN Electric P8 2.9: автоматическая генерация схемы подключения клеммника

## 1. Цель проекта

Разработать Add-in для EPLAN Electric P8 2.9, который по команде пользователя:

1. Позволяет выбрать существующий клеммник.
2. Позволяет выбрать ориентацию отчёта: горизонтальную или вертикальную.
3. Позволяет указать точку вставки на заранее созданной странице.
4. Штатными средствами EPLAN создаёт встроенный отчёт клеммника на основе соответствующей формы `.f11`.
5. После создания отчёта автоматически определяет точки подключения клемм по служебным якорным линиям внутри созданной группы графики.
6. Анализирует реальные соединения EPLAN Data Model.
7. Автоматически создаёт графические линии от клемм к кабелям/назначениям.
8. Создаёт символ кабеля `544 / SHCP2`.
9. Для одного кабеля поддерживает подключения одновременно с обеих сторон клеммника.
10. Поддерживает ветвление нескольких линий в одну точку кабельного символа.
11. Для соединений без кабеля создаёт только соответствующую графическую линию.
12. Не дублирует текст обозначения кабеля, так как обозначение кабеля уже формируется самой формой отчёта.
13. Использует фактическое свойство `Место сборки` для ссылок назначения.

Главный принцип реализации: **форма отвечает за визуальное расположение и задаёт координаты подключения через служебные невидимые линии, Add-in отвечает за анализ электрических связей и построение дополнительной графики.**

# 2. Принятые архитектурные решения

## 2.1. Форма `.f11` остаётся настраиваемой пользователем

Не вычислять координаты подключения по фиксированным смещениям, размерам строк и внутренней геометрии формы.

Пользователь может изменять:

- ширину формы;
- высоту строк;
- расстояние между строками;
- положение графики;
- положение текстов;
- размеры элементов формы;
- положение кабельных обозначений.

Add-in не должен зависеть от этих конкретных размеров.

## 2.2. Якорь реализуется обычной графической линией

В форме для каждой строки клеммника размещается служебная линия-якорь.

Требования к якорю:

- тип объекта: `Line`;
- слой: `EPLAN430 — Размещение свойства.Обозначения выводов клемм`;
- свойство линии: `Невидимый`;
- линия не должна печататься;
- в рабочем поле EPLAN она может быть видна служебным цветом при необходимости;
- линия проходит через всю ширину соответствующей строки клеммника.

Для горизонтальной формы:

- начало/конец линии интерпретируются соответственно как верхняя/нижняя точки подключения.


Для вертикальной формы:

- начало линии = левая точка подключения;
- конец линии = правая точка подключения.


Не создавать отдельный специальный тип объекта `AnchorTerminal`.

> **Статус (Этап 1–3, rev.13/rev.6.x): механизм НЕ реализован — SUPERSEDED.**
> Якорная линия `Line` на `EPLAN430` не доживает до страницы: при вставке формы EPLAN
> переименовывает автослой `EPLAN430` → `EPLAN450` (слияние таблиц слоёв формы и
> страницы, summary п.9), в дереве отчёта объектов на `EPLAN430`/`EPLAN200` нет (п.12).
> Фактический якорь — дескрипторы `PlaceHolderText` ряда/столбца номеров формы (п.26):
> текст = номер клеммы, `SourceObject` = Terminal (запасной путь `[PHFB]`, rev.6.1).
> Точки подключения берутся из геометрии выводов (К3', п.11–13), не из якорной линии.
> Реализованный фильтр — §8.2, сопоставление — §8.4. Урок rev.9: для переноса на другой
> проект слои формы стоит делать пользовательскими с уникальными именами (TSA — отменено
> пользователем 20.09.2026, автонумерация `EPLANnnn` устраивает).

## 2.3. Слой является признаком машинного якоря

При анализе созданного `ReportBlockReference` Add-in ищет среди вложенной графики линии, удовлетворяющие условиям:

- объект является графической линией;
- объект расположен на `EPLAN430`;
- объект имеет свойство `Невидимый`. (на тестовом этапе не проверять для визуального контроля пользователем)

Остальная графика формы не должна участвовать в поиске якорей.

> **Статус (Этап 1–3): SUPERSEDED** — см. §2.2 Статус: слой `EPLAN430` не сохраняется
> при слиянии таблиц слоёв формы и страницы; признак якоря — числовой текст дескриптора
> `PlaceHolderText` в доминирующем ряде/столбце номеров формы (§8.2), не слой линии.

## 2.4. Источник электрической информации — Data Model

Нельзя определять кабель только по визуальному тексту отчёта.

Необходимо получать информацию из EPLAN Data Model:

- `TerminalStrip`;
- `Terminal`;
- `Terminal.ExternalConnections`;
- `Terminal.ConnectionInfo`;
- `Connection`;
- `ConnectionDefPoints`;
- `Cable` / `CableDefinitionLine` / `CableConnections` в зависимости от фактической структуры проекта.

В качестве базовой единицы анализа использовать **конкретное `Connection`**, а не просто связь `Terminal -> Cable`.

Это необходимо для случаев, когда:

- у одной клеммы есть подключения с разных сторон;
- с разных сторон подключены разные кабели;
- один и тот же кабель подключён к клеммам с обеих сторон;
- присутствуют несколько соединений на одной клемме;
- присутствуют мосты, многопозиционные или многоуровневые клеммы.

# 4. Модели данных

## 4.1. `TerminalStripModel`

Представляет выбранный клеммник.

Минимальный состав:

```text
TerminalStripModel
├── Id
├── Name
├── Terminals[]
└── CableLayouts[]
```

## 4.2. `TerminalModel`

```text
TerminalModel
├── TerminalReference
├── Number
├── SortOrder
├── Position
├── AnchorLine
└── Connections[]
```

`Position` не должна быть единственным источником координат. Основной источник графической позиции — якорь из формы.

## 4.3. `AnchorLineModel`

```text
AnchorLineModel
├── StartPoint
├── EndPoint
├── Orientation
└── TerminalKey
```

Для горизонтальной формы:

```text
LeftPoint  = StartPoint
RightPoint = EndPoint
```

Для вертикальной формы:

```text
TopPoint    = StartPoint
BottomPoint = EndPoint
```

На этапе разрешения якорей допускается сохранить исходные точки и затем нормализовать их относительно ориентации.

> **Статус (Этап 3): модель в исходном виде не используется.** Якорь — не линия, а
> дескриптор `PlaceHolderText` (номер клеммы + позиция в доминирующем ряду/столбце);
> `AnchorResolver` строит `AnchorMap` (номер → TerminalKey → колонка), точки подключения
> — из геометрии выводов (К3'), колонки — из стубов К4. `TerminalKey` сохранён (rev.6.1:
> полное имя клеммы из DM). См. §8.2/§8.4.

## 4.4. `TerminalConnectionModel`

Это главная модель конкретного подключения.

```text
TerminalConnectionModel
├── Terminal
├── Connection
├── ConnectionPoint
├── Side
├── Cable
├── HasCable
├── Destination
└── ConnectionDesignation
```

`Side` принимает как минимум:

```text
Left
Right
Top
Bottom
Unknown
```

Не ограничивать модель правилом «один кабель на одну сторону».

## 4.5. `CableModel`

```text
CableModel
├── Name
├── Connections[]
├── LeftConnections[]
├── RightConnections[]
├── OtherConnections[]
└── SymbolPosition
```

`CableModel` является группировкой подключений одного физического/логического кабеля.

## 4.6. `CableLayoutModel`

Пример:

```text
CableLayoutModel
├── Cable = K142
├── LeftConnections
│   ├── XT1:15
│   └── XT1:16
├── RightConnections
│   ├── XT1:18
│   └── XT1:19
└── SymbolPosition
```

# 5. Этап 1 — исследовательский прототип API EPLAN 2.9

До разработки полного Add-in необходимо сделать маленький тестовый проект/тестовый Add-in.

## 5.1. Проверить создание встроенного отчёта

Проверить через EPLAN API 2.9:

- создание `ReportBlockReference` через механизм embedded report;
- получение созданного блока отчёта;
- доступ к его `SubPlacements`;
- доступ к вложенной графике после генерации отчёта.

## 5.2. Проверить якорную линию

Создать тестовую `.f11` с несколькими строками и невидимыми `Line` на `EPLAN430`.

После генерации отчёта проверить:

1. Сохраняется ли линия внутри графики `ReportBlockReference`.
2. Какой тип объекта возвращает API.
3. Доступны ли её координаты.
4. Доступно ли свойство слоя.
5. Доступно ли свойство `Невидимый`.
6. Сохраняется ли направление линии.
7. Как выглядят координаты после размещения/масштабирования отчёта.

Результат этого теста должен быть зафиксирован до реализации основной геометрии.

## 5.3. Проверить отсутствие ложных совпадений

Убедиться, что штатная графика формы не создаёт дополнительные линии, которые случайно удовлетворяют критериям:

```text
Line + EPLAN430 + Invisible
```

Если EPLAN уже использует такие объекты в штатной форме, дополнительно определить критерий идентификации якоря.

# 6. Этап 2 — подготовка форм `.f11`

Нужны две формы:

```text
Клемник_ОУ(горизонтально).f11
Клемник_ОУ(вертикально).f11
```

## 6.1. Добавить Anchor Line

В каждую строку формы добавить одну невидимую линию.

Горизонтальная форма:

```text
<LEFT---------------------------RIGHT>
```

Вертикальная форма:

```text
TOP
 |
 |
 |
BOTTOM
```

## 6.2. Поместить якорную линию на `EPLAN430`

Она должна иметь свойство `Невидимый`.

## 6.3. Не менять назначение других слоёв

Существующие объекты формы остаются на штатных слоях, например:

- `EPLAN450 — Специальные тексты.Тексты заполнители`;
- `EPLAN200 — Графика.Формы`.

## 6.4. Не добавлять кабельный текст для Add-in

Текст обозначения кабеля должен продолжать формироваться самой формой отчёта.

Add-in не должен дополнительно рисовать этот текст возле линии.

# 7. Этап 3 — чтение клеммника из Data Model

Создать `EplanTerminalStripReader`.

Задачи:

1. Получить выбранный `TerminalStrip`.
2. Получить список его терминалов.
3. Получить порядок/обозначения терминалов.
4. Для каждого терминала получить внешние соединения.
5. Для каждого соединения получить `ConnectionInfo`.
6. Определить конкретный `Connection`.
7. Найти связанные connection definition points.
8. Определить связанный кабель, если он существует.
9. Сохранить данные в `TerminalConnectionModel`.

Не использовать парсинг текста отчёта для определения кабеля.

# 8. Этап 4 — разрешение якорей

Создать `AnchorResolver`.

## 8.1. Получение всех кандидатов

Обойти графику `ReportBlockReference` и собрать все объекты, удовлетворяющие критериям якоря.

## 8.2. Фильтрация

**Реализовано (Этап 3, rev.5.5–6.2):** фильтр якорей — дескрипторы `PlaceHolderText`
(исходный вариант `Line + EPLAN430 + Invisible` не реализуем — см. §2.2 Статус):

```text
Type == PlaceHolderText
текст (Contents / GetDisplayString) парсится как номер клеммы
  ИЛИ SourceObject == Terminal — запасной путь [PHFB] (rev.6.1)
позиция — в доминирующем ряду (Horizontal, по Y) / столбце (Vertical, по X) номеров формы
```

Примечания API 2.9: `PlaceHolderText.Text` нет — только `Contents` (MultiLangString) /
`GetDisplayString()` (summary п.26); `SourceObject` дескриптора = Terminal (п.26).
Доминирующий ряд/столбец = бакет 0.1 мм с максимумом числовых дескрипторов (порог ≥2) —
отсекает паразитные числовые тексты других строк формы (п.26: 106 коллизий в rev.5.5).

Исходный план (SUPERSEDED) — для каждого кандидата проверить:

```text
Type == Line
Layer == EPLAN430
Invisible == true
```

## 8.3. Определение координат

Сохранить:

- начало;
- конец;
- длину;
- ориентацию;
- координаты в системе координат страницы.

## 8.4. Сопоставление якоря строке клеммника

**Реализовано (Этап 3, rev.5.6–6.2):**

1. колонки клемм = центры стубов-маркеров (`EPLAN100`, L ≤ 1 мм) + виртуальные колонки
   под перемычками стубов (шаг сетки = нижняя медиана шага стубов) — К4 (summary п.16);
2. якорь (номер из дескриптора, §8.2) привязывается к ближайшей колонке по оси
   ориентации: Horizontal — X (ряд Y=-81.0), Vertical — Y (столбец X=99.0) — п.33–34;
3. `AnchorMap`: номер → TerminalKey (полное имя клеммы из DM, rev.6.1); дубль номера —
   `[KEYDUP]` WARN «первый побеждает»;
4. раздвоения (К2): мост с одним листом на якоренной колонке и вторым на неякоренной —
   слот привязывается к клемме якоренного листа (`[SPLIT]`, п.27);
5. порядковая схема «колонка i ↔ клемма i» НЕ используется и как fallback НЕ возвращается
   (опровергнута п.25–26; решение пользователя п.26).

Из исходных вариантов ниже реализованы: 2/3 (координата Y/X) — через якоря-дескрипторы;
4 (положение терминального объекта) — запасной путь `SourceObject=Terminal` (`[PHFB]`,
не задействовался ни на одном стенде — обе формы имеют числовой ряд/столбец номеров).

Основной вариант — определить соответствие по геометрии/положению строки.

Не зашивать фиксированный шаг строк.

В зависимости от фактической структуры `ReportBlockReference` возможны варианты:

1. сопоставление с вложенной строкой/группой;
2. сопоставление по координате Y для горизонтального отчёта;
3. сопоставление по координате X для вертикального отчёта;
4. использование положения реального терминального объекта, если EPLAN предоставляет его после генерации отчёта.

Предпочтение отдавать наиболее структурному способу, если API его реально предоставляет.

## 8.5. Контроль качества

После сопоставления должно выполняться:

```text
Количество ожидаемых строк == количество найденных якорей
```

либо выдаётся диагностическая ошибка.

Дополнительно проверить, что каждой строке соответствует ровно один якорь.

# 9. Этап 5 — определение стороны подключения

Для каждого `TerminalConnectionModel` определить сторону относительно строки формы.

Горизонтальная форма:

```text
Anchor.StartPoint → LEFT
Anchor.EndPoint   → RIGHT
```

Вертикальная форма:

```text
Anchor.StartPoint → TOP
Anchor.EndPoint   → BOTTOM
```

Для соединения необходимо учитывать реальную сторону подключения терминала, полученную из Data Model, а не выбирать сторону только по наличию кабеля.

Если API предоставляет точное соответствие connection point / side — использовать его.

Не делать допущение:

```text
одна клемма = максимум один Connection с каждой стороны
```

Создать `CableLayoutBuilder`.

Для каждого `TerminalConnectionModel`:

```text
if Cable != null
    добавить в CableLayoutModel
else
```

## 10.1. Группировка

Ключ группировки должен соответствовать объекту кабеля/уникальной сущности Data Model, а не только текстовой строке, если EPLAN позволяет получить идентификатор объекта.

Имя кабеля используется для отображения/диагностики.

## 10.2. Двустороннее подключение одного кабеля

Обязательный сценарий:

```text
K142
├── Left
│   ├── XT1:15
│   └── XT1:16
└── Right
    ├── XT1:18
    └── XT1:19
```

Все ветви должны сходиться к одному `SHCP2`.

# 11. Этап 7 — расчёт геометрии кабеля

Создать `CableGeometryBuilder`.

## 11.1. Входные данные

```text
CableLayoutModel
+
Anchor coordinates
+
Page coordinates
+
Orientation
```

## 11.2. Простой случай

Один connection → один cable symbol:

```text
XT1:1 ───────── ● K142
```

## 11.3. Несколько соединений одной стороны

```text
XT1:1 ─────────┐
XT1:2 ─────────┤
               ● K142
```

## 11.4. Подключения с двух сторон

```text
XT1:1 ─────────┐
XT1:2 ─────────┤
               ● K142
XT1:5 ─────────┤
XT1:6 ─────────┘
```

При этом положение кабельного символа должно рассчитываться так, чтобы все ветви подключались к одной точке символа.

## 11.5. Правила геометрии

Геометрию не привязывать к конкретному номеру клеммы.

Сначала необходимо определить алгоритм раскладки:

1. собрать все точки одной стороны;
2. определить центральную/опорную точку кабеля;
3. построить общую магистраль;
4. построить ответвления от anchor points к магистрали;
5. довести магистраль до точки вставки `SHCP2`;
6. проверить отсутствие самопересечений насколько это возможно.

Правила геометрии должны быть вынесены в отдельный класс и не смешиваться с чтением EPLAN Data Model.

# 12. Этап 8 — создание графических линий

Создать `GraphicLineCreator`.

Линии должны быть **графическими**, а не электрическими `Connection`, поскольку пользовательский чертёж использует графические линии.

Для каждой рассчитанной ветви:

1. создать `Line`;
2. установить начальную точку;
3. установить конечную точку;
4. применить требуемый слой/графические свойства;
5. не добавлять текст кабеля.

Не изменять уже созданную графику отчёта без необходимости.

Все созданные Add-in объекты рекомендуется помечать способом, который позволит впоследствии отличать их от объектов формы и корректно обновлять результат. Конкретный механизм маркировки выбрать после проверки доступных свойств EPLAN 2.9.

# 13. Этап 9 — создание символа кабеля 544 / SHCP2

Создать `CableSymbolCreator`.

Использовать реальный EPLAN символ/вариант, а не рисовать круг вручную.

Задачи:

1. определить используемую библиотеку/идентификатор символа `544 / SHCP2` в проекте;
2. проверить программное создание символа через EPLAN API;
3. разместить символ в рассчитанной точке;
4. при необходимости установить необходимые свойства/обозначение кабеля;
5. связать графические линии с точкой кабельного символа визуально.

Не дублировать название кабеля отдельным текстовым объектом, если его уже отображает форма отчёта.

# 14. Этап 10 — ссылки назначения / `Место сборки`

Создать `DestinationReferenceCreator`.

Источником данных должна быть соответствующая сущность EPLAN Data Model.

Не хардкодить строку назначения.

Для каждого connection, где требуется ссылка назначения:

1. получить значение свойства `Место сборки`;
2. создать/разместить штатный EPLAN break-point/reference symbol;
3. установить нужное свойство;
4. проверить правильное отображение на странице.

Нужно использовать настоящий EPLAN-объект ссылки, а не просто рисовать текст, если API и структура проекта это позволяют.

# 15. Этап 11 — соединения без кабеля

# 22. Что не делать

Не использовать следующие подходы как основной механизм:

### Не вычислять координаты по фиксированному шагу

Например:

```text
Y = Y0 + index * 7.5
```

Это сломается после изменения формы.

### Не искать клемму по номеру на графике

Номер в форме — представление отчёта, а не надёжный источник Data Model.

### Не искать кабель по тексту отчёта

Кабель должен определяться через EPLAN Data Model.

### Не использовать `AnchorTerminal` как отдельный тип объекта

Якорь является обычной графической линией формы.

### Не рисовать кабельный текст Add-in'ом

Его уже формирует форма отчёта.

### Не использовать EPLAN electrical Connection для декоративных линий

Для этой задачи требуются графические линии.

### Не предполагать «один кабель на сторону»

Архитектура должна поддерживать произвольное количество `Connection`.

# 24. Критерии готовности MVP

MVP считается реализованным, когда выполняются все условия:

1. Пользователь выбирает клеммник.
2. Пользователь выбирает горизонтальную/вертикальную форму.
3. Отчёт создаётся штатными механизмами EPLAN.
4. Add-in находит якоря — дескрипторы `PlaceHolderText` числового ряда/столбца номеров формы (исходный критерий «Anchor Lines на `EPLAN430`» не реализуем — §2.2 Статус).
5. Для каждой строки определяется точка подключения.
6. Data Model корректно определяет реальные `Connection`.
7. Cable определяется из Data Model.
8. Один кабель может подключаться к нескольким строкам.
9. Один кабель может иметь подключения с обеих сторон клеммника.
10. Все ветви одного кабеля сходятся к одному SHCP2.
11. Соединения без кабеля отображаются как обычные графические линии.
12. Кабельные обозначения не дублируются.
13. Ссылки назначения используют `Место сборки`.
14. Изменение размеров и расположения элементов `.f11` не ломает подключение линий.
15. Вертикальная форма работает по тому же принципу.
16. Повторная генерация не создаёт неконтролируемых дубликатов.

# 25. Главный принцип для Coding Agent

**Не писать генератор как набор специальных условий под текущий чертёж.**

Генератор должен строиться вокруг следующих сущностей:

```text
EPLAN Data Model
      ↓
TerminalConnection
      ↓
Anchor Line из формы
      ↓
Геометрическая точка
      ↓
CableLayout
      ↓
Geometry Engine
      ↓
Graphic Lines + SHCP2 + Destination References
```

Форма определяет **где** подключаться.

Data Model определяет **что с чем соединено**.

Geometry Engine определяет **как провести линии**.

Graphics Layer создаёт **итоговые объекты EPLAN**.

Это разделение должно сохраниться на протяжении всей реализации.

> **Уточнение (Этап 3):** «Anchor Line из формы» — фактически якоря-дескрипторы
> `PlaceHolderText` ряда/столбца номеров формы (§2.2 Статус, §8.2); точки подключения —
> из геометрии выводов (К1–К4). Разделение сущностей сохранено: форма определяет **где**
> (колонки/якоря), DataModel — **что с чем** (`Connection` + №31058), Geometry Engine —
> **как**.
