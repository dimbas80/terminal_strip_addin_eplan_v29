# Code Review: SymbolBrowserDialog.cs / SymbolCatalog.cs

## 1. Общая оценка

Текущая архитектура в целом соответствует поставленной задаче:

* основной элемент каталога — `Symbol`, а не отдельный `SymbolVariant`;
* для одного символа предусмотрено 8 ячеек предпросмотра `A–H`;
* используется `DrawingService` для графического отображения символов;
* категории должны строиться на основе `FunctionDefinition`;
* пользователь выбирает конкретный вариант символа;
* после выбора должны возвращаться:

  * имя библиотеки;
  * имя символа;
  * номер варианта.

Переписывать решение целиком не требуется.

Однако перед дальнейшей разработкой необходимо исправить несколько логических проблем.

---

# 2. Критическая проблема №1 — выбранный вариант не должен определяться через ComboBox

## Проблема

В `SymbolBrowserDialog` уже есть `_nSelectedCell`, который соответствует выбранной ячейке предпросмотра.

Это правильный источник информации о выбранном варианте.

Но существующие свойства вроде:

```csharp
VariantH
VariantV
```

используют состояние ComboBox / выбранные индексы.

Это не соответствует новой логике интерфейса.

Пользователь выбирает вариант **кликом по одной из 8 ячеек A–H**, поэтому результат выбора должен определяться именно через выбранную `SymbolVariant`.

## Что изменить

Добавить в результат диалога отдельное свойство:

```csharp
public SymbolVariant SelectedVariant { get; private set; }
```

или, если безопаснее не возвращать объект API наружу:

```csharp
public int SelectedVariantNr { get; private set; }
```

Желательно хранить одновременно:

```csharp
public SymbolCatalogEntry SelectedSymbol { get; private set; }

public SymbolVariant SelectedVariant { get; private set; }
```

При клике по ячейке:

```text
SelectedSymbol = текущий Symbol
SelectedVariant = вариант соответствующий ячейке
```

# 3. Критическая проблема №2 — не использовать индекс ячейки как единственный источник VariantNr

Сейчас логика фактически предполагает:

```text
A = 0
B = 1
C = 2
...
H = 7
```

Для интерфейса это правильно.

Но нельзя делать вывод:

```csharp
VariantNr = index;
```

если реальные данные `SymbolVariant` уже доступны.

Необходимо строить соответствие:

```text
ячейка A -> SymbolVariant с VariantNr = 0
ячейка B -> SymbolVariant с VariantNr = 1
...
ячейка H -> SymbolVariant с VariantNr = 7
```

То есть перед построением UI создать:

```csharp
Dictionary<int, SymbolVariant>
```

Например:

```csharp
var variantsByNumber =
    symbol.Variants.ToDictionary(v => v.VariantNr);
```

После этого:

```csharp
for (int i = 0; i < 8; i++)
{
    if (variantsByNumber.TryGetValue(i, out var variant))
    {
        // ячейка существует
    }
    else
    {
        // ячейка отсутствует
    }
}
```

Это принципиально лучше, чем определять наличие варианта через `Count`.

# 4. Критическая проблема №3 — убрать предположение «если данные неизвестны, значит есть только A»

Сейчас есть fallback-логика, которая при невозможности определить варианты фактически интерпретирует ситуацию как:

```text
есть только вариант A
```

Это опасно.

Неизвестно ≠ отсутствует.

Необходимо различать три состояния:

```text
Variant существует
Variant отсутствует
Информация о Variant недоступна
```

Минимально:

```csharp
bool variantsKnown;
```

Если API реально вернул `Symbol.Variants`, использовать только эти данные.

Если данные получить не удалось — не надо автоматически показывать A как существующий вариант.

Лучше:

* отключить ячейки;
* показать диагностическую информацию;
* либо использовать fallback только там, где это действительно необходимо.

# 5. Критическая проблема №4 — результат OK должен содержать конкретный Variant

При нажатии `OK` необходимо проверить:

```text
выбран Symbol?
выбран Variant?
```

Если Symbol выбран, но вариант не выбран:

```text
не разрешать завершить выбор
```

Логика должна быть примерно такой:

```csharp
if (SelectedSymbol == null)
{
    // сообщение: выберите символ
    return;
}

if (SelectedVariant == null)
{
    // сообщение: выберите вариант A–H
    return;
}

DialogResult = DialogResult.OK;
```

После закрытия диалога основной код должен иметь возможность получить:

```text
LibraryName
SymbolName
VariantNr
```

Например:

```csharp
SelectedSymbol.LibraryName
SelectedSymbol.SymbolName
SelectedVariant.VariantNr
```

# 6. Критическая проблема №5 — выбор должен хранить объект, а не только строку

Сейчас выбор символа частично определяется через строку:

```csharp
_strSelectedSymbol
```

а затем символ повторно ищется по имени.

Это нежелательно.

Проблема:

* одинаковые имена символов могут встречаться в разных библиотеках;
* повторный поиск усложняет код;
* можно случайно получить другой объект;
* выбранный вариант уже существует в момент клика и его нет смысла искать заново.

## Рекомендация

Хранить непосредственно выбранную запись каталога:

```csharp
private SymbolCatalogEntry _selectedSymbol;
```

и конкретный вариант:

```csharp
private SymbolVariant _selectedVariant;
```

Тогда цепочка становится:

```text
клик по SymbolCard
        ↓
_selectedSymbol
        ↓
клик по A–H
        ↓
_selectedVariant
        ↓
OK
        ↓
результат
```

Без повторного поиска по строкам.

# 7. Модель SymbolCatalogEntry желательно сделать более полной

Сейчас запись каталога фактически содержит:

```text
Symbol Name
Function Definition
```

Для текущего UI этого недостаточно.

Желательно, чтобы `SymbolCatalogEntry` представлял конкретный символ и содержал данные, необходимые UI.

Минимально:

```csharp
class SymbolCatalogEntry
{
    public Symbol Symbol { get; }

    public string LibraryName { get; }

    public string SymbolName { get; }

    public FunctionDefinition FunctionDefinition { get; }

    public SymbolVariant[] Variants { get; }
}
```

Конкретные типы/свойства адаптировать под фактические API EPLAN 2.9.

Главная идея:

> Catalog Entry должен быть связан с реальным `Symbol`, а не только с его строковым именем.

# 8. Поиск сейчас недостаточно функциональный

Это важное требование.

Пользователь не всегда знает имя символа.

Например, он может искать:

```text
автоматический выключатель
```

или:

```text
контактор
```

или:

```textпредохранитель
```

При этом название самого символа может быть совершенно другим.

Поэтому поиск должен работать не только по:

```text
Symbol.Name
```

но и по данным `FunctionDefinition`.

Необходимо включить в поисковый индекс:

```text
Symbol Name
Library Name
FunctionDefinition.Name
FunctionDefinition.Description
FunctionDefinition.CategoryName
FunctionDefinition.CategoryRegion
FunctionDefinition.GroupName
FunctionDefinition.MainGroup
```

Также следует учитывать:

```text
FUNC_CATEGORY
FUNC_CATEGORY_REGION
FUNC_GROUP
FUNC_DESC
```

если эти данные доступны непосредственно у `Symbol`.

# 9. Поиск должен проходить по функциональной классификации

Основная цель использования `FunctionDefinition` — повторить логику классификации EPLAN.

Структура должна быть примерно:

```text
Trade
 └── Area
      └── Category
           └── Group
                └── Function Definition
                     └── Symbols
```

Необходимо использовать именно данные EPLAN, а не создавать собственную искусственную классификацию.

Для этого использовать:

```csharp
project.FunctionDefinitionLibrary.FunctionDefinitions
```

и свойства:

```csharp
MainGroup
CategoryRegion
CategoryName
GroupName
Name
Description
```

# 10. Фильтрация дерева при поиске

При поиске необходимо учитывать не только совпадение непосредственно с названием узла.

Например:

```text
Автоматические выключатели
    ├── Символ 1
    ├── Символ 2
    └── Символ 3
```

Если пользователь ищет:

```text
выключатель
```

и совпадение находится на уровне `FunctionDefinition`, должны отображаться соответствующие дочерние символы.

То есть поиск должен быть рекурсивным:

```text
совпадает Symbol
        OR
совпадает FunctionDefinition
        OR
совпадает родительская категория
        ↓
показываем Symbol
```

Необходимо не просто фильтровать названия верхних узлов.

# 11. BuildCellList() необходимо упростить

Сейчас `BuildCellList()` имеет несколько вариантов получения данных:

* из реального `SymbolVariant`;
* через повторное создание `Symbol`;
* через строки;
* через fallback.

Для EPLAN API 2.9 основным путём должен быть:

```text
Symbol
   ↓
Symbol.Variants
   ↓
SymbolVariant
```

То есть:

```csharp
SymbolVariant[] variants = symbol.Variants;
```

и дальше работать непосредственно с ними.

Fallback оставить только если он действительно нужен для совместимости.

Не надо строить несколько параллельных механизмов получения одного и того же объекта.

# 12. Отображение A–H

Требование интерфейса:

Каждый `SymbolCard` представляет **один Symbol**.

Внутри:

```text
┌───────────────────────────────┐
│ Symbol Name                   │
├────────┬────────┬────────┬────┤
│   A    │   B    │   C    │ D  │
│ preview│ preview│ preview│... │
├────────┼────────┼────────┼────┤
│   E    │   F    │   G    │ H  │
│ preview│ preview│ preview│... │
└────────┴────────┴────────┴────┘
```

Каждая ячейка должна соответствовать конкретному:

```csharp
SymbolVariant
```

а не просто индексу.

# 13. DrawingService

Использование `DrawingService` для предпросмотра — правильное направление.

Для каждого варианта:

```text
SymbolVariant
       ↓
DrawingService
       ↓
DisplayList
       ↓
Paint
```

Важно:

`DisplayList` не должен создаваться заново при каждом `Paint`.

Правильная схема:

```text
создание/изменение варианта
        ↓
CreateDisplayList()
        ↓
сохранить DisplayList
        ↓
Paint → DrawDisplayList()
```

Это позволит избежать лишней работы при перерисовке окна.

# 14. DrawingService и количество объектов

Сейчас потенциально создаётся до 8 `DrawingService` на один `SymbolCard`.

Это допустимо для первой рабочей версии.

Но при отображении большого количества символов может возникнуть проблема производительности:

```text
100 SymbolCards × 8 вариантов
=
800 preview
```

Поэтому пока не нужно усложнять архитектуру, но желательно предусмотреть возможность:

```text
lazy rendering
```

или виртуализации.

То есть не обязательно сразу отрисовывать все 800 вариантов.

Однако это оптимизация второго этапа. Сначала добиться корректной работы.

# 17. Приоритет исправлений

Исправления выполнять в следующем порядке.

### P0 — обязательно

1. Хранить выбранный `SymbolCatalogEntry`.
2. Хранить выбранный `SymbolVariant`.
3. Передавать `VariantNr` выбранного варианта в результат.
4. Использовать реальные `SymbolVariant.VariantNr`.
5. Исправить проверку `OK`.
6. Убрать fallback `unknown variants → A`.

### P1 — обязательно для полноценного поиска

7. Расширить поиск на:

   * Symbol Name;
   * Library Name;
   * FunctionDefinition Name;
   * Description;
   * Category;
   * Group;
   * Area;
   * MainGroup.
8. При совпадении категории/FunctionDefinition показывать соответствующие дочерние символы.

### P2 — улучшение архитектуры

9. Сделать `SymbolCatalogEntry` полноценным объектом символа.
10. Минимизировать повторное получение `Symbol`/`SymbolVariant`.
11. Упростить `BuildCellList()`.

### P3 — оптимизация

12. Проверить производительность большого количества `SymbolCard`.
13. При необходимости перейти на lazy rendering / virtualized preview.
14. Кэшировать DisplayList там, где это возможно.

# 18. Критерии готовности

Реализация считается корректной, если выполняются все условия:

* [ ] Каталог строится на основе `FunctionDefinition` EPLAN.
* [ ] Один `SymbolCard` соответствует одному `Symbol`.
* [ ] В карточке отображаются варианты A–H.
* [ ] Каждая ячейка A–H соответствует реальному `SymbolVariant`.
* [ ] Отсутствующий вариант отключён.
* [ ] Неизвестный набор вариантов не интерпретируется как «есть только A».
* [ ] Клик по варианту сохраняет конкретный `SymbolVariant`.
* [ ] Нельзя нажать OK без выбранного варианта.
* [ ] Результат содержит:

  * [ ] LibraryName;
  * [ ] SymbolName;
  * [ ] VariantNr.
* [ ] Поиск работает по имени символа.
* [ ] Поиск работает по Function Definition.
* [ ] Поиск работает по описанию/категории/группе.
* [ ] При совпадении родительской категории отображаются дочерние символы.
* [ ] Preview использует `DrawingService`.
* [ ] DisplayList не создаётся заново при каждом `Paint`.
